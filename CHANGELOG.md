## 1.4.4 (2026-11-26)
MTU, tests and the Quality page rebuilt on Ali's 22 agreed rules (he said the 1.4.3 behaviour was wrong for him: a number that changed by itself, one verdict word, no way to see what a test really did). This version replaces the automatic MTU completely: **nothing changes the size of a live tunnel any more.**
- **Rules 1-3, one number:** the MTU and MRU of a live tunnel are fixed; any change happens only by disconnect and connect. Each side announces only its MRU (the peer's MRU becomes our sending limit), so the file gets `mtu N` and `mru N` with the same number; the panel shows one name, "MTU". Settings hold one default for dial-in (`mtu_default_in`) and one for outgoing (`mtu_default_out`); an outgoing connection may have its own `mtu` (it replaces the default); dial-in clients share the one inbound number (a per-client `mtu` is not used any more; 1280 only when Settings has nothing). `mtu = auto` of older versions is read as "the default". The old keys `mtu_max`, `mtu_step` (per site), `mtu_margin`, `mtu_auto_min`, `mtu_auto_max_day` are ignored. (gw: `mtu_value`, `dialin_announce`, `dir_val`; web: `eff_mtu`, `dir_def`)
- **Rules 4, 9, 11, 14, 15, 21, the test:** every `test_every` minutes (default 1; Settings in/out, own value per connection) a full test sends `ping_count` pings (default 10; 3-30: more would not fit in the minute) to the far end of the tunnel and, if the connection has one, to its own test address (`test_addr`); loss, delay, jitter are measured for both. The percent answered is `answered/sent*100`, rounded. The last test is kept in `quality/NAME.last` (`far=loss,avg,max,jit ded=... ded_addr=...`); the minutes between tests write a short log line (`up` and dashes + byte counters). `quality-sample` is one run under a lock; **Test now** (`mtu-verify`, button) forces a full test (Q_FORCE). (gw: `quality_cb`, `quality_run`, `pingstat`, `tst_cfg`, `cmd_mtu_verify`)
- **Rules 6, 19, own test address:** `test_addr` per connection (IPv4, not 0./127./224-239./255., unique across ALL connections, outgoing and dial-in; checked by `validate_test_settings` and by the panel). It gets a host route with metric 1 through its own tunnel (`test_route_set`; set again at every minute and by the ip-up hook through `mtu-apply IFACE`). The own address never replaces the far end: both are always tested. The Measure MTU page (`mtu-test ADDRESS INTERFACE`) with address AND channel adds a temporary route (metric 1), sends the DF packets, proves the way (routing table + packet counter of the tunnel: "Proof: ..." or "NOT PROVEN"), and removes the route. The "+101" warning is gone everywhere.
- **Rules 5, 15-18, 20, size test:** each test starts from the CURRENT MTU of the tunnel (that is the ceiling) and sends `ping_count` DF packets of exactly that size (the quality ping is a normal size). A problem is "packet too big" message OR (small packets answered >= 71% AND big packets < 71%): then it steps down by 5 (`mtu_step_in/out`), one step per minute (`mtu_step_wait_in/out`) so a firewall does not see a burst, separately for each address; when a size passes the result is "suggested MTU" (states in `mtu-test/NAME.far|ded`: ok / stepping / found / floor / none). Nothing is changed or cut by the test. The floor (`mtu_min`, default 1250; own value per connection, else `mtu_min_in/out`) is never crossed: at the floor only a warning label appears. Small packets under 71% = "no usable answer" (state none, no stepping). A tunnel that is down is "no measurement" (rule 22): no pings, the old results are removed. (gw: `mtu_probe`, `bigping`, `mtu_live`)
- **Rules 7, 8, 13, cut on save:** every Save of a connection cuts that tunnel once (dial-in client: disconnect only, the router dials in again by itself; outgoing: disconnect and connect again), after a warning in the form. A change in the Settings cuts all dial-in tunnels once when an inbound value changed, all outgoing ones when an outbound value changed (separately; the alert limits cut nothing). New commands `cut NAME`, `cut-all in|out`. A structural change of an outgoing site (host, secret, routes ...) still goes through `apply` (it restarts all services; that already reconnects everything). (gw: `cmd_cut`, `cmd_cut_all`; web: `bg_cut`, `save`, `dialin_save`, `settings` handler, `CUTMSG_*`, `cutAsk`)
- **Rules 9, 10, 21, 22, the Quality page:** the overall word ("Quality: Fair") and its grade column are gone. Each connection shows ring circles with the percent answered in the middle (24 h connected time, far end, own address; colours 0 black, 1-40 brown, 41-70 red, 71-95 orange, 96-100 green; a black one is a full black disc), the delay and the swing coloured by multiples of a base (up to 1x green, 2x orange, 4x red, 6x brown, above black; base `rtt_base` default 50 ms, `jit_base` default 20 ms; Settings in/out, own value per connection), the speed, the connection time and the result of the size test of both addresses ("1400 passes", "measuring...", "suggested 1380", "even at the lowest size 1250 the packet is too big", "no measurement"). The connection page shows the same circles for the last test and the suggested MTU. The Sites and Dial-in lists show the MTU chip (green passes, amber suggested, red problem) and a plain "Quality" link. (web: `pct_col`, `base_col`, `ring`, `cv`, `read_last`, `addr_cell`, `read_mtutest`, `mtu_phrase`, `mtu_cell`, `quality_page`, `conn_page`)
- **Measure MTU page:** channel + address form; below it a table of all connections with the last result of both addresses, and **Test now** (a forced test of everything: if the size passes the same number shows, if too big stepping starts and "measuring..." shows until it ends). "Use N for X" appears only for outgoing sites (and cuts the tunnel); a dial-in client has no number of its own. (web: `mtu_page`, `mtu_run`, `mtu_verify`, `mtu_set`)
- **Settings page:** two blocks, "Outgoing connections" and "Dial-in clients": MTU, lowest MTU the test may reach, step, minutes between steps, pings per test, test every, delay base, swing base (keys `KEY_out` / `KEY_in` in quality.conf; the older plain `mtu_min` is still read). Connection forms: own MTU (outgoing only), own test address, lowest MTU, pings, interval, bases. (web: `dir_fieldset`, `tests_fieldset`, `check_pq`, `check_site_tests`)

## 1.4.3 (2026-11-26)
MTU rebuilt after Ali's tests (the router showed 1280 although he set 1250-1450 and auto chose 1379; every connection got the same number; the panel said "35 min connected" right after a reconnect). He described the logic he wants and it replaces the old measurement-by-formula completely.
- **Why it was wrong:** (1) the shared dial-in pppd file had `mtu 1280` / `mru 1280` written in the code, so every router saw 1280 whatever the range said; (2) auto did not measure the road: with no answer from the far router it assumed 1500 and used `1500 - 101 - 20 = 1379` for every connection; (3) the test raised our link to 1500 before pinging, so a packet that was split outside counted as "passes"; (4) the outside address of a dial-in client was found only when exactly one client was connected (three were), so "road not measured" appeared; (5) connection time came from the minute log, which cannot see a disconnect shorter than a minute.
- **New auto logic** (`mtu_auto_cb`, `mtu_auto_run`, `mtu_auto_change`; no formula, no 1500 assumed, no margin): the link starts at the highest allowed size (`mtu_max`, or the size found last time). About 1 minute after a new link is up a packet of exactly the MTU is sent to the far end of the tunnel (DF ping, nothing raised). If it passes: left alone. If not: down by `mtu_step` (default 20, new key, replaces `mtu_margin`, which is still read and ignored) until a size passes, never below `mtu_min`; the change is written to the pppd file and the tunnel is disconnected and connected again, because the far router learns the size only at connect. Every `mtu_auto_min` minutes (default 30): the current size is tested again (failing: same step down); when it passes, `+mtu_step` is tested (the link is raised for that one test and put back); when that passes it is tried by a reconnect (`NAME.trial`), and if it does not pass after the reconnect the old size is restored and no new try is made for 6 hours (`NAME.upfail`). `mtu_auto_max_day` (default 6) still limits changes in 24 h; nothing passes in the whole range = told once, size left alone; no answer to a tiny ping = told once after 3 times. Every change: watch.log, Events, Telegram.
- **Fixed size is never touched.** `mtu_verify_cb` (every 5 minutes, already existed for the chip) now also warns once (log, Events, Telegram) when a fixed size does not pass two checks in a row, and says when it passes again.
- **No hard-coded size:** a connection with no `mtu` uses the default of Settings (`mtu_default_out` for outgoing sites, `mtu_default_in` for dial-in clients, both in quality.conf; each can be a number or `auto`; 1280 only when Settings has nothing). (gw: `mtu_value`, `qconf_val`; web: `eff_mtu`, Settings page, connection forms)
- **Dial-in clients:** all clients share ONE pppd options file and pppd offers its size before it knows who calls (login comes after), and xl2tpd can pick a different file per client only by the client's IP address. So the size the routers see is one shared number: the biggest any client may use (a fixed number, or the top of an auto client's range; no client: the Settings default) (`dialin_announce`, written by `apply` and by `dialin-sync` through `dialin_mtu_rewrite`, no restart). Our own side of each dial-in link follows the test (`mtu_auto_change` changes the live link in place; no reconnect because the router cannot be told a different number anyway). See KNOWN-ISSUES.
- **Manual test (`l2tp-gw mtu-test NAME`, "Measure MTU" page):** tests the size the tunnel has NOW: passes or not, and if not the biggest size that passes (down by `mtu_step`); nothing is raised or changed; `RESULT` has the new field `pass=yes|no`. The road outside is shown as information only (it never decides). The address-test path no longer raises the link to 1500 and no longer assumes 1500 for the outside road. (gw: `mtu_check_site`, `mtu_measure`; web: `mtu_page`)
- **Address of each dial-in client:** from its own tunnel: pppd's pid file (`/var/run/IFACE.pid`) -> `pppol2tp_tunnel_id` in the process command line -> `ip l2tp show tunnel` ("From a to b"); if that cannot be read and only one dial-in IPsec SA exists, that one; otherwise "not known" (never a guess). (gw: `ppp_pid`, `ppp_peer_public`, `mtu_find_cb`, `quality_cb`)
- **Real connection time:** `l2tp-gw link-info` prints `NAME IFACE SECONDS PUBLIC_ADDRESS` per connected site (seconds = age of the pppd process, `ps -o etimes`). The panel uses it for the Quality "Connection time" and the connection page, and a reconnect the minute log did not see now counts as a drop (`q_sessions(rows, now, age)`). **Dial-in page:** each connected client shows "router address" and "connected for" (before: neither). (web: `link_info`, `link_age`, `dialin_list_html`)
- Settings page: new boxes `mtu_step`, `mtu_default_out`, `mtu_default_in`; "Safety margin" removed. `q_dur` shows seconds under one minute.
- Tests: new `dev/t37/run.sh` (49 checks, ping stub refuses a DF packet bigger than the link MTU like the real ping); the old `dev/t35` (formula logic) is removed. Real-server proof still needed (see KNOWN-ISSUES): `ip l2tp show tunnel` format, pid file names.
- Repo layout (2026-11-26, owed from 1.4.2): the GitHub repo is flat (all files in the root, no folders) because Ali's zip upload had put the files in the root and 1.4.2 never installed. `install.sh` and `make-installer.sh` accept the flat layout first and fall back to `bin/ docs/ dev/`; PROJECT-MEMORY.md has the rules (GitHub tools, test extraction).

## 1.4.0 (2026-11-25)
Automatic MTU with a range, router limit (MRU) care, road and UDP diagnostics (requested by Ali: "between 1250 and 1400, a bit lower than measured, careful about MRU, auto or manual per connection, the helpful alarms, and an answer for UDP").
- **`mtu = auto`** per connection (sites.conf; a number still means a fixed size). Range keys `mtu_min` (default 1250), `mtu_max` (1400), `mtu_margin` (20 bytes) per connection, defaults in `quality.conf`, plus defaults-only `mtu_auto_min` (measure every N minutes, default 30, minimum 5) and `mtu_auto_max_day` (changes per 24 h, default 6). Checked by `validate_mtu_range` / `check_pq`. Settings page: new box "Automatic MTU"; connection forms: MTU box accepts `auto` and shows the three range boxes. (gw: `mtu_cfg`, `mtu_is_auto`, `mtu_offer`, `mtu_set_value`; web: `mtu_fieldset`, `PQ_KEYS`, `KEYS`)
- **How the size is chosen** (`cmd_mtu_auto` / `mtu_auto_cb` / `mtu_auto_run`, started detached by the watcher every minute with its own lock; each connection is measured at most every `mtu_auto_min` minutes, at once when its interface is new; at most 3 measured in parallel): `mtu_measure` gives the biggest size that passes inside the tunnel and (outer road - 101); target = that value minus `mtu_margin`, kept inside the range and never above the router's MRU (an exact limit: no margin on it). pppd is given `mtu_max` (what we offer/accept), the live link is set to the learned value (start value before the first measurement = `mtu_min`; kept by `mtu-apply`, the ip-up hook and `dialin-sync`, now also for outgoing sites).
- **Safeguards:** two matching measurements (within 20 bytes) in a row before anything changes; a change smaller than 30 bytes is ignored unless the current size does not pass any more (then it is lowered after two measurements); no answer to ping = no change (told once after 3 times); at most `mtu_auto_max_day` changes a day (then told once); every change goes to watch.log, the Events page and Telegram (when the quality alert is on). A connection with a fixed number or empty MTU is never touched (that is the off switch).
- **Router limit (MRU):** when the live size of a new link is below what we offered, the router asked for that (`st/mtu-auto/NAME.mru`; for dial-in clients "offered" is 1280, the shared pppd option). The target never goes above it; below `mtu_min` it only tells you once.
- **Road and UDP diagnostics** (file `mtu-road/NAME`: time, outer road, inner max, suggested, split-packet result, router limit, link MTU): after each measurement a ping bigger than the MTU without "do not fragment" is sent through the tunnel to see whether split packets arrive (big UDP such as DNS answers). New health lines per tunnel: automatic MTU and range, "UDP: packets up to N bytes pass whole", WARN "MTU + about 101 bytes of wrapping is more than the outside road: packets are split outside", WARN when split packets are lost, WARN when the router allows less than the MTU. Connection page rows: Automatic MTU, Road outside the tunnel, Split packets (big UDP), Router limit (MRU) (`mtu_road_rows`). The MTU chip shows "MTU auto N".
- **UDP answer:** MSS only helps TCP. UDP needs (1) a size that fits the whole wrapped road, (2) ICMP "packet too big" not blocked (existing health line), (3) split packets surviving (new test). Honest limit: the 101 bytes of wrapping are an estimate; the road is measured with ping, so a network that drops ping but passes data cannot be measured (then "no answer", no change).
- Tests: new `dev/t35/run.sh` (46 checks, ping stub with separate limits for inside, outside and split packets); others unchanged.

## 1.2.1 (2026-11-25)
TCP size (MSS) fixed in both directions per tunnel; checks for it (Ali: services stall through the tunnels, "packets lose part of their data").
- **Why:** the old rule `-j TCPMSS --clamp-mss-to-pmtu` (setup) only looks at the interface a packet LEAVES by. A SYN from the router that goes out to the Internet (interface ens5) kept its big MSS (1460), so the Internet server sent packets that were too big for the tunnel (MTU 1350/1400) and only path-MTU discovery (ICMP) could save the connection. Found by reading the real server's `iptables -t mangle -L FORWARD -v` and the `ppp` MTUs Ali sent.
- **New chain `L2TPGW-MSS`** (mangle, jumped to from the top of FORWARD): for every `ppp*` interface two rules, `-i DEV` and `-o DEV`, `TCPMSS --set-mss (link MTU - 40)`. `--set-mss` never raises a value. New command `l2tp-gw mss-apply`; it runs at the end of `mtu-apply` (so the ip-up hook, `dialin-sync` and `apply` refresh it) and every minute from the watcher; the chain is rebuilt only when the list of tunnels or an MTU changed (signature in `/var/lib/l2tp-gw/mss-sig`). The old generic rule stays as a second layer. (gw: `cmd_mss_apply`, `cmd_mtu_apply`, `cmd_watch`)
- **Health lines:** server: generic clamp present; per-tunnel rules (count and how many connection starts they looked at); no firewall rule drops ICMP "packet too big" (a rule that drops only ping is fine). Per tunnel (outgoing and dial-in): "TCP size (MSS) is cut to N both ways (link MTU M)" or a WARN with `l2tp-gw mss-apply`. (gw: `cmd_check`, `check_site`, `check_server_site`; captured in a variable first because `iptables | grep -q` can die of SIGPIPE under pipefail)
- **Connection page** shows "TCP segment size (MSS)" and "Biggest UDP packet that passes whole" (link MTU - 28). UDP cannot be clamped: it needs the right MTU, working ICMP and (for DF packets) a path that really carries the size.
- Tests: new `dev/t33/run.sh` (17 checks, own iptables stub with per-table rules); all others unchanged.

## 1.1.0 (2026-11-25)
Connection quality monitoring (users complained about slow/choppy links that get better after a reconnect).
- **Measuring every minute** (`l2tp-gw quality-sample`, called by the watcher): 5 quick pings through each tunnel (`-I ppp-NAME`, to the peer address) and 5 pings outside the tunnel to the router's real address (dial-in client: the one IPsec peer, when there is exactly one). One line per site and minute in `/var/lib/l2tp-gw/quality/NAME.log`: `time up|down loss avg max jitter outloss outavg outmax rx_bytes tx_bytes`. 7 days are kept (pruned at 10200 lines); the log of a deleted site is removed with it. A tunnel that is down gets a `down` line. (gw: `pingstat`, `quality_cb`, `cmd_quality_sample`, `cmd_watch`)
- **Speed** comes from the interface byte counters (average and busiest minute per window), not from a speed test: it shows what the users really use, not the top speed of the line.

## 1.0.5 (2026-11-25)
MTU: is the SET value really passing, and what does the router allow?
- **Check of the set MTU (`l2tp-gw mtu-verify [NAME]`):** for every connected tunnel it sends one ping of exactly the set size (DF, through the tunnel, the link is not touched). States in `/var/lib/l2tp-gw/mtu-status`: `ok` (passes), `bad` (the set size does NOT pass now), `lowered` (the router asked for a smaller size when the tunnel came up), `unknown` (no answer even to a tiny ping: no false alarm). The watcher runs it every 5 minutes (parallel, about 10 s at most); the panel ignores results older than 20 minutes. (gw: `mtu_verify_cb`, `cmd_mtu_verify`, `cmd_watch`)
- **Panel:** the MTU chip on Sites and Dial-in is green when the size passes, amber when it does not pass or when the router allows less ("MTU 1400: router allows 1360"), plain when it cannot be checked. The Measure MTU page lists the state of every connection and has a "Check now" button. (web: `mtu_status`, `mtu_chip`, `/mtu/verify`)
- **Measuring shows the router's own limit (MRU):** when a tunnel came up with a smaller link MTU than the one set here, the peer asked for less (pppd takes the smaller). `mtu-test` says so and never suggests more than that. Before, the test raised the link to 1500 and hid it. `RESULT` has the new field `lowered=` (0 = not lowered). Not possible: reading the router's MRU when it is equal to or bigger than what is set here; then we only know it is not smaller. MRRU belongs to multilink only, which is not used: keep it off on the MikroTik.

## 1.0.4 (2026-11-25)
Fix: the MTU of a dial-in client was not kept after the client reconnected, and the Dial-in page did not show it.
- **Cause:** the ip-up hook that sets the MTU (`mtu-apply`, new in 1.0.3) is written only by `l2tp-gw apply`. After an update without `apply` the old hook stayed, so a reconnect went back to 1280. **Fix:** `dialin-sync` (also run by every Dial-in save in the panel) now rewrites the hooks too; it touches no tunnel. (gw: `cmd_dialin_sync` calls `write_route_hooks`)
- **Dial-in page:** each client now shows an "MTU N" chip (1280 when empty), like the Sites page. (web: dial-in rows)
- **MTU measuring was too optimistic (found by Ali: it said 1500 while the other end was limited to 1400).** Cause: a big packet can pass INSIDE the tunnel only because the outside packets are cut into pieces on the internet road; the ping still gets an answer, so "no limit" was reported. **Fix:** for a named tunnel `mtu-test` now also measures the road to the far router (outgoing site: its address; dial-in client: its public address, only when exactly one is connected over IPsec; otherwise 1500 is assumed and said) and suggests the smaller of "passes inside" and "road minus 101 bytes of wrapping (IPsec + L2TP + PPP)". With a 1500 road this gives 1399, close to the usual 1400. The text says clearly why. `RESULT` has two new fields `inner=` and `outer=` (outer=0: not measured). A plain address is measured as before (no wrapping). The measurement still cannot see a smaller limit that the MikroTik itself sets (max-mtu / MRU): use the MikroTik command shown on the page to make both ends agree. (gw: `cmd_mtu_test`, `mtu_find_cb`; web: `mtu_page`)
- Tests: t29 has 8 more checks (42): hook rewritten by dialin-sync, live MTU applied, reconnect puts the MTU back, chip on the Dial-in page.
- To get the fix on a running server after the update: `l2tp-gw dialin-sync` (no tunnel is interrupted). The MTU of an outgoing site still needs the next reconnect or `l2tp-gw apply`.
